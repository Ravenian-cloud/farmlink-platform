# Phase 4: Security hardening and compliance readiness

This checklist is a technical baseline, not a certification or legal opinion. FarmLink processes personal, identity and payment-related data; requirements depend on the countries where users and services operate. Obtain local privacy, financial-services and payment-provider counsel before launch.

## Verified controls and gaps

- Marketplace writes (listing, bids and transaction actions) require `kyc_status=verified`. KYC status can be changed only through the JWT-authenticated, `KYC_ADMIN_IDS`-allowlisted admin review route. It permits `pending -> verified/rejected` and `rejected -> pending`, requires a documented reason, prohibits self-review, and records reviewer, target, old/new status, reason and timestamp in append-only audit storage. The database rejects audit updates/deletes. The request accepts no role or identity fields.
- KYC review is not identity verification automation: the assigned reviewer must inspect evidence outside this workflow using an approved, secure process before choosing a status. The API does not collect or store evidence. Do not put identity documents, identity numbers, or other sensitive evidence in the audit reason; record a concise decision rationale. Define evidence handling, retention, appeal, periodic re-check, and audit-access policies before launch.
- The production Apache image adds `nosniff`, frame denial, a referrer policy and HSTS headers. The web frontend is hosted separately and must receive its own reviewed CSP and security-header policy.
- Phase 5 partner credentials are random one-time-issued keys stored only as SHA-256 hashes; revoke or reissue them using the backend console commands. Partner access still needs contractual scope, operational rotation and monitoring.
- Phase 5 ad creatives are stored on private application storage and are served only for approved active campaigns. Image type/size checks and manual review are present; malware scanning and retention automation remain launch prerequisites.
- The API uses bearer JWTs, login/registration throttles, idempotency guards and M-Pesa callback reconciliation. Set a short production access-token lifetime (`JWT_TTL`, for example 900 seconds) and implement a reviewed refresh/revocation/session policy before launch. The current JWT middleware has no server-side revocation list.
- HTTPS/TLS protects traffic between clients, the load balancer, and services when correctly configured. This is **not end-to-end encryption**: the API must process request data in plaintext. Do not claim E2E encryption or that all transaction data is encrypted end-to-end.
- GCP-managed disk/database encryption at rest and Secret Manager protect infrastructure data and credentials, but do not replace application-level access controls, retention limits, or field-level protection. The existing app stores KYC status but no KYC documents. Avoid collecting identity documents until a secure, purpose-limited storage and deletion design is approved.
- M-Pesa payment status and escrow are simulated application state. Daraja STK Push does not provide conditional escrow custody. A licensed provider, reconciliation, refund/dispute process, and legal review are prerequisites for any real escrow/payout claim.

## Required production configuration

1. **Transport:** Enforce HTTPS at the Google external load balancer; disable HTTP ingress; use managed certificates and confirm renewals. Restrict backend and Cloud SQL traffic to the private VPC. Configure Laravel's trusted proxy list to the actual GKE/load-balancer proxy ranges; do not trust arbitrary forwarded headers. Keep TLS versions/cipher policy aligned with Google Cloud's supported secure frontend policy.
2. **Secrets and identities:** Generate unique production `APP_KEY`, JWT signing secret, database password, Daraja credentials and webhook secret. Put them in Secret Manager, grant the GKE workload identity access only to the exact secret resources it needs, rotate with a runbook, and alert on access anomalies. Do not log authorization headers, secrets, callback payloads containing personal data, or full payment details.
3. **Database:** Use a least-privilege application database role, private IP, regional HA, automated backups and point-in-time recovery. Restrict admin access, use separate staging/prod projects, encrypt backups, test recovery, and monitor privileged queries and connection saturation.
4. **Application:** Keep `APP_DEBUG=false`; set `APP_ENV=production`; validate all input server-side; use prepared ORM/query-builder operations; retain role/ownership checks in addition to KYC checks; apply per-user/IP/provider rate limits and request-size limits; keep dependencies patched; and return generic errors without stack traces or personal data.
5. **Authorization and KYC:** Set `KYC_ADMIN_IDS` in both deployment ConfigMaps to comma-separated UUIDs of approved reviewers; keep the list least-privileged and do not leave it empty in production. Reviewers must manually check evidence outside this API using the approved secure evidence process; the workflow does not verify identities automatically. Define evidence requirements, MFA, separation of duties, audit access/retention, appeal and periodic re-check processes, plus a break-glass procedure. Require authorization at every resource operation; do not rely on obscurity or frontend hiding.
6. **Payment/webhooks:** Keep callbacks idempotent and verify the provider's expected identifiers, amount, currency and final status by provider-supported reconciliation. Use TLS and provider IP allowlists/signatures where supported, but do not treat an unguessable URL or a shared secret alone as proof of authenticity. Alert on duplicates, amount mismatch, delayed callbacks and reconciliation drift.
7. **Web and mobile:** Store mobile tokens in platform secure storage, not general preferences; avoid sensitive data in analytics/crash reports; set a restrictive web Content Security Policy on the web host; configure exact CORS origins; protect upload endpoints with size/type/content scanning and private storage if added; and review dependency/SBOM output for every release.
8. **Observability and incident readiness:** Centralize structured logs, redact PII, restrict log readers, set retention, record security-relevant admin/KYC/payment actions, and alert on abuse patterns. Maintain incident contacts, severity levels, evidence preservation, credential rotation, user/regulator notification decision trees and a tested service/data recovery procedure.

## Privacy and compliance release checklist

- Map data categories, collection purpose, lawful basis/consent, processors, cross-border transfers, retention and deletion for each launch jurisdiction.
- Publish understandable privacy notices and terms, and provide appropriate access/correction/deletion/complaint routes. Define what must be retained for financial or fraud obligations with counsel.
- Conduct a privacy impact assessment for KYC, location matching, profiling/analytics and third-party data. Keep location coarse and optional unless exact location is necessary and consented to.
- Suppress small analytics cohorts; the initial market baseline requires at least five recent completed trades per crop/county/unit/currency cohort. Validate re-identification risk against the actual data.
- Review vendor agreements, data residency, breach reporting timelines, cross-border transfer mechanisms, consumer-protection rules, payment regulations and financial promotion claims.
- Obtain an independent penetration test and privacy/security review, remediate critical/high issues, and document accepted residual risk before public launch.

## Correcting common security claims

Use “TLS-encrypted in transit” for network transport and describe managed/database encryption-at-rest accurately. Do not promise “guaranteed security,” “end-to-end encryption,” “compliant with all data protection laws,” or real escrow custody. Compliance depends on jurisdiction, operating practices, contracts and independent assessment.
